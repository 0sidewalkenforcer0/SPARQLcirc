Probabilistic query evaluation over knowledge graphs

Shared provenance circuits, built by the query engine itself

How a SPARQL query is rewritten so that an unmodified engine materializes one shared, content-addressed provenance circuit for all answers — which we then compile and weighted-model-count into exact answer probabilities. A walkthrough on the paper's drug-interaction running example, with the real input and output at every stage.

reification: RDF-standard / SPARQL-star fragment: BGP · UNION · OPTIONAL · MINUS semiring: spm (⊕ ⊗ ⊖) verified vs possible-world enumeration
The running example

One shared triple is the whole problem

A drug-interaction KG where every interactsWith edge is an extracted fact holding with a calibrated probability. We ask which drugs Aspirin reaches in exactly three hops:

input · probabilistic KG (reified)
# each edge is a triple with an identity (token) and a probability
d:p1 Aspirin  →iw→ Warfarin    Pr = .92
d:p2 Warfarin →iw→ Metformin   .87
d:p3 Metformin→iw→ Omeprazole  .85   ← shared
d:p4 Aspirin  →iw→ Ibuprofen   .78
d:p5 Ibuprofen→iw→ Metformin   .71
d:p6 Warfarin →iw→ Lisinopril  .65
d:p7 Lisinopril→iw→Clopidogrel .60
input · query
PREFIX d: <urn:d:>
SELECT ?z WHERE {
  d:Aspirin d:iw ?x .
  ?x        d:iw ?y .
  ?y        d:iw ?z .
}

Two answers. Clopidogrel comes from one path; Omeprazole from two paths that share the edge p3.

why you can't just multiply and add Omeprazole's provenance is (p1⊗p2⊗p3) ⊕ (p3⊗p4⊗p5). Treating the two paths as independent gives 1−(1−.92·.87·.85)(1−.78·.71·.85) = 0.8308 — but the shared p3 makes them dependent, so the correct value is 0.85·[1−(1−.92·.87)(1−.78·.71)] = 0.7743. Naive independence over-counts by 7.3%. Recovering the correct number means keeping the sharing explicit and compiling it — which is exactly what the pipeline below does.
The workflow, end to end

Five stages: query → circuit → probability

The engine never changes. The rewriting turns provenance annotation (a string per answer, as in NPCS/SPARQLprov) into provenance compilation (one shared circuit for all answers), which the client then compiles and counts.

 query + reified KG
      │  A. rewrite
      ▼
 NPCS-style string  ──►  B. gate constructors instead of string ops
      │
      ▼  C. emit ONE construct (or a plan of INSERTs)
 CONSTRUCT query ──► [ unmodified SPARQL engine ] ──► D. shared circuit as RDF (a DAG)
                                                          │  E. compile + weighted model count
                                                          ▼
                                                    exact Pr(answer)

Stage A–B  rewrite → per-answer polynomial

Start from NPCS: reify each triple, name every match

Each triple pattern s p o is rewritten to bind a fresh statement token ?fprovN — the identity of the matching triple. A join becomes a product ⊗; grouping the answers becomes a sum ⊕. NPCS emits this as a string:

output · NPCS rewriting (verbatim, reproduced Java — 139/139 identical to the original)
SELECT ?z (CONCAT("⊕(", GROUP_CONCAT(?fjoin0), ")") AS ?finalprovennacevariable)
WHERE {
  ?fprov0 rdf:subject d:Aspirin ; rdf:predicate d:iw ; rdf:object ?x .
  ?fprov1 rdf:subject ?x        ; rdf:predicate d:iw ; rdf:object ?y .
  ?fprov2 rdf:subject ?y        ; rdf:predicate d:iw ; rdf:object ?z .
  BIND(CONCAT("(⊗", STR(?fprov0), ",", STR(?fprov1), ",", STR(?fprov2), ")") AS ?fjoin0)
} GROUP BY ?z
the limitation we remove The output is a string per answer. The shared p3 is spelled out twice; sharing across answers (p1) is invisible; and the factored structure a probability computation needs must be re-parsed back out of the text. So we keep NPCS's rewriting skeleton but change what the operators emit.

Stage C  γ: gate constructors → a CONSTRUCT the engine runs

Emit gates, not text — as a CONSTRUCT query

We replace ProvProd / ProvAggSum / ProvDiff with gate constructors and emit a CONSTRUCT. Run on the engine, it produces the circuit as RDF triples. The key trick: each gate gets a content-addressed IRI — a deterministic hash of its operator and children — computed inside SPARQL. Equal gates get equal IRIs, so the engine's set semantics share them automatically.

output · emitted CONSTRUCT (real; the ⊗-gate id is content-addressed in SPARQL)
CONSTRUCT {
  ?t a c:Times ; c:in ?a0 ; c:in ?a1 ; c:in ?a2 ; c:feeds ?ans .
  ?ans a c:Plus ; c:answer ?anskey .
} WHERE {
  ?a0 rdf:subject d:Aspirin ; rdf:predicate d:iw ; rdf:object ?x .
  ?a1 rdf:subject ?x ; rdf:predicate d:iw ; rdf:object ?y .
  ?a2 rdf:subject ?y ; rdf:predicate d:iw ; rdf:object ?z .
  # content-addressed ⊗ id: hash each token, SORT the hashes, hash the tuple
  BIND(SHA256(STR(?a0)) AS ?srt0)  BIND(SHA256(STR(?a1)) AS ?srt1)  BIND(SHA256(STR(?a2)) AS ?srt2)
  BIND(IF(?srt0 <= ?srt1, ?srt0, ?srt1) AS ?srt3)   # comparator
  BIND(IF(?srt0 <= ?srt1, ?srt1, ?srt0) AS ?srt4)   # network
  BIND(IF(?srt4 <= ?srt2, ?srt4, ?srt2) AS ?srt5)   # (pure SPARQL 1.1)
  BIND(IF(?srt3 <= ?srt5, ?srt3, ?srt5) AS ?srt7) ...
  BIND(IRI(CONCAT("urn:g:t:", SHA256(CONCAT("T|",?srt7,"|",?srt8,"|",?srt6)))) AS ?t)
  BIND(IRI(CONCAT("urn:g:a:", SHA256(CONCAT("A|z=",STR(?z))))) AS ?ans)
}

Leaves need no work: ?fprov binds to the triple's statement-node IRI, so a token is its own leaf node — every gate that references p3 emits c:in d:p3, and RDF merges them into one shared leaf.

Stage E  compile + weighted model count

Compile the circuit, count, get the exact probability

The client reads the circuit, compiles it to a d-DNNF-family target (an OBDD or SDD), and runs weighted model counting — linear in the compiled size. Because p3 is one shared leaf, the count handles the dependency correctly instead of double-counting it.

output · answer probabilities (checked against possible-world enumeration)

Clopidogrel     p1⊗p6⊗p7                       0.358800   0.358800  ✓
Omeprazole      (p1⊗p2⊗p3) ⊕ (p3⊗p4⊗p5)     0.774298   0.774298  ✓

3 · Union ⊕ — branches feed one shared answer gate

SELECT ?y WHERE { { :Alice :knows ?y } UNION { :Alice :likes ?y } }

y=Carol  | ⊕(⊗t2)

Bob    ← ⊕( ⊗t1, ⊗t4 )   # one ⊕, two branches

how the union happens Each branch is its own CONSTRUCT, but both compute the same answer-gate id hash("A|y=Bob"). So the ⊗t1 gate (knows) and the ⊗t4 gate (likes) both c:feeds the one shared ⊕ node — content-addressing turns "two branches" into "one ⊕" with no coordination.

SELECT ?y (CONCAT("⊕(", GROUP_CONCAT(?u0), ")") AS ?prov) WHERE {

4 · Minus ⊖ — keep the left, subtract the matching right

SELECT ?y WHERE { :Alice :knows ?y  MINUS { :Alice :blocks ?y } }
NPCS · string per answer
y=Bob    | ⊖(⊕⊗t1, ∅)          # not blocked
y=Carol  | ⊖(⊕⊗t2, ⊕⊗t5)   # blocked by t5
ours · shared circuit (4 CONSTRUCTs)
Bob    ← ⊖( ⊕⊗t1 , ∅ )
Carol  ← ⊖( ⊕⊗t2 , ⊕⊗t5 )
the plan (4 CONSTRUCTs) 
# ours — the ⊖ needs the left sum, the right sum, and their join:
C1  left  products → ⊕P1(?y)          # :knows matches
C2  right products → ⊕P2(?y)          # :blocks matches
C3  for each compatible ?y: ⊕P2 c:feeds ⊕sub(?y)   # the part to subtract
C4  ?m a c:Minus ; c:minuend ⊕P1 ; c:subtrahend ⊕sub ; c:feeds ?answer
# Bob: no :blocks match ⇒ ⊕_sub empty ⇒ ⊖(⊕⊗t1, ∅). Carol: ⊖(⊕⊗t2, ⊕⊗t5).
# NPCS emits the same structure as a nested SELECT … OPTIONAL … CONCAT("(⊖",…) string.

5 · Optional ⊗ ⊕ ⊖ — (matched: join) ⊕ (unmatched: minus)

SELECT ?y ?c WHERE { :Alice :knows ?y  OPTIONAL { ?y :city ?c } }
NPCS · string per answer
y=Bob  c=Rome | ⊕(⊗t1,t6)            # matched
y=Bob  c=∅    | ⊖(⊕⊗t1, ⊕⊗t6)     # the "unmatched" part
y=Carol c=∅   | ⊖(⊕⊗t2, ∅)          # no city at all
ours · shared circuit (5 CONSTRUCTs)
(Bob,Rome)  ← ⊗(t1,t6)              # AND-branch
(Bob,NULL)  ← ⊖(⊕⊗t1, ⊕⊗t6)      # DIFF-branch
(Carol,NULL)← ⊖(⊕⊗t2, ∅)

OPTIONAL is exactly (P1 AND P2) ⊕ (P1 DIFF P2): the join branch (5th CONSTRUCT) handles matched rows, the 4-CONSTRUCT DIFF plan handles the c=NULL rows. Same non-monotone ⊖ as above. Here DIFF is the algebra's anti-join (the negative half of OPTIONAL), not the user keyword MINUS — they differ when the operands share no variable (DIFF removes, MINUS is a no-op).

6 · Property paths ⊕⊗ — recursive reachability, finite on cyclic graphs

?x :p+ ?y asks for reachability — recursive, and infinite to enumerate on a cyclic graph. We build a finite circuit in the absorptive semiring PosBool (idempotent ⊕/⊗: a pair is reachable once, however many paths witness it) by a level-indexed fixpoint:

reach⁰(u,v)      = edge u→v
reach^k+1(u,v) = reach^k(u,v) ⊕ ⊕_w [ reach^k(u,w) ⊗ edge(w,v) ]

The level k is baked into each reach gate's id, so a level-(k+1) gate points only at level-≤k gates — the circuit is an acyclic DAG even though the data has a cycle. Recursive sharing (pointing at the single gate reach^k(u,w), not an expanded path list) keeps it polynomial: a ring of n nodes → ≈n² gates; a clique stays polynomial while #simple-paths ~ e·(n−2)!.

cyclic A→B→C→A, shortcut A→C · A :p+ ?y
y=B  ← ⊕( ⊗e1 )
y=C  ← ⊕( ⊗e3, ⊗(e1,e2) )
y=A  ← ⊕( ⊗(e4,e3), ⊗(e4,e1,e2) )
WMC (e1..e4 = .9,.8,.5,.7) == possible-world enum
A→B  0.900000   # only edge into B
A→C  0.860000   # e3 ∨ e1·e2
A→A  0.602000   # e4·(e3 ∨ e1·e2)

Technical challenges & how we solved them

The six problems on the path from strings to probabilities

01 · representation

Per-answer strings can't be shared or compiled

NPCS/SPARQLprov emit one serialized polynomial per answer; shared subterms are rewritten at every occurrence and the factored structure must be re-parsed.

Solution. Keep NPCS's rewriting skeleton but make the operators emit gates as RDF via a CONSTRUCT. The engine builds one graph for all answers — no decoding pass.

02 · sharing

How does the engine know two gates are the same?

An engine has no notion of "the same gate". Without it, every derivation makes fresh nodes and nothing is shared.

Solution. Content-addressed gate IRIs: IRI(hash(op, children)) computed in SPARQL with SHA256+CONCAT. Equal gates → equal IRI → RDF set-semantics dedupes. Leaves share for free (a token is its statement node).

Reproduces Fig. 2: p1, p3 each referenced by two gates
03 · canonicalization

A product key uses an unordered multiset

A self-join yields ⊗(t1,t2) and ⊗(t2,t1) — the same gate in two orders. They must collapse to one. But an order-invariant multiset hash from SUM+COUNT is not injective ({1,4} vs {2,3} collide) — wrong merges give wrong probabilities.

Solution. A comparator network in pure SPARQL 1.1: hash each child to fixed-width hex, sort the hashes (retaining repeats), concatenate with unambiguous delimiters, then hash again. The pre-hash key is canonical and order-independent; the final SHA-256 id is collision-resistant. Ordinary duplicate RDF edges subsequently fold at the documented Boolean/PQE serialization boundary.

Sorted-key regressions + Boolean circuit WMC == possible-world enumeration
04 · non-monotonicity

OPTIONAL and MINUS need a monus ⊖

SPARQL's OPTIONAL/MINUS are non-monotone; commutative semirings can't express them. And the monus gate's subtrahend is an aggregate — it doesn't fit one CONSTRUCT.

Solution. A short plan of CONSTRUCT/INSERT passes realizing P1 OPTIONAL P2 = (P1 AND P2) ⊕ (P1 DIFF P2): build the per-side sums, then ⊖(minuend, Σ subtrahend); an empty subtrahend keeps the row.

MINUS & OPTIONAL: WMC == possible-world enumeration
05 · size

A flat circuit is exponential for many-path queries

Building one ⊗ per full derivation makes the circuit as large as the number of derivations — |data|#patterns.

Solution. Factored construction by variable elimination, run as multi-pass INSERTs: join the relations mentioning a variable (⊗), then marginalize it (⊕), sharing intermediates. Circuit size drops to fixed degree treewidth+1.

chain query: flat W⁴ (38,416) → factored 3W² (588) at W=14; same result
06 · exact probability

Counting is #P-hard — where is it tractable?

The shared structure makes derivations dependent; exact probability is #P-hard in general.

Solution. Compile the circuit to a d-DNNF-family target and weighted-model-count in linear time in the compiled size. This is polynomial for lineage of bounded treewidth — the tractable island; the compiler realizes the n·2O(tw) bound.

OBDD & SDD both == possible-world enumeration on every circuit
